The public questionnaire 500 took roughly 50 minutes to resolve. The limiting factors were observability, IAM-action coverage, and deployment granularity—not lack of test breadth or reasoning capacity.

What to encode next

1Live-incident skill + script assets

SkillMissing

Codify the exact sequence: stage/account preflight, request correlation, structured log lookup, effective-principal inspection, focused probe, narrow deployment choice, readback, cleanup, then final validation.

Why this layer: this is a judgment-guided, repeatable workflow with commands and safety checks. It is too procedural for AGENTS.md and does not require a specialist subagent.

2Provider-error observability contract

Shared helper + testPartly encoded

Every provider catch that returns a generic 500 should log a sanitized error name/code, service request ID, application request ID, and transaction cancellation codes—never tokens, bodies, or credentials.

Why this layer: the current change fixes the journal path. A shared helper plus deterministic test prevents the same diagnostic-deploy tax in the next AWS integration.

3IAM action-coverage gate

CI / hookPartly encoded

Derive required IAM actions from the transaction primitives actually used. A ConditionCheck must imply dynamodb:ConditionCheckItem; the gate should fail if the runtime role or permissions boundary lacks it.

Why this layer: the new verifier checks a declared action list, but the list itself can be incomplete. This is deterministic and should fail before deployment, not live traffic.

4Approved narrow deployment automation

Script / workflowMissing

Provide two explicit test-stage paths: Lambda code-only update and owner-managed boundary sync. Both must assert the canonical target, render desired state from source, show a scoped diff, apply, read back, preserve rollback, and refuse production.

Why this layer: SST --target still evaluated and built unrelated components. The direct IAM path worked in seconds, but ad hoc commands should become a reviewed, repeatable operation.

5Safe identity preflight everywhere

Reusable utilityIncomplete

Resolve the profile through STS, compare it with deployment-targets.json, and print only safe identity metadata. Never choose a profile by its name and never dump raw AWS config while diagnosing.

Why this layer: the repository already states the account invariant, but maintenance and hotfix paths can bypass the deployment verifier. One utility should guard all AWS operations.

6Focused probe catalog

Skill assetMissing

Keep small disposable probes for public first save, authenticated API access, private file access, and invitation acceptance. Each probe creates invented data, reports the request ID, and cleans up idempotently.

Why this layer: the real endpoint probe was decisive. Turning temporary scripts into maintained assets removes quoting failures and avoids broad browser/E2E setup.

Recommended encoding order

  1. Generalize the structured provider-error helper and cover generic-500 boundaries with tests.
  2. Add the derived IAM action gate so transaction primitives and effective boundary permissions cannot drift.
  3. Build reviewed test-only scripts for identity preflight, log correlation, boundary sync, Lambda-only update, and disposable probes.
  4. Wrap those assets in auditflow-live-incident, with a stop condition that escalates to full SST/E2E only when the narrow path is unsafe or insufficient.
