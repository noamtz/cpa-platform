Resolve the skill collision at the routing surface.

A supplied AuditFlow test-stage API 404 was incorrectly treated as a browser-testing task. The missing capability was not diagnosis; it was precise selection between two overlapping skills.

Smallest durable fix: broaden auditflow-live-incident from only “5xx/403” to unexpected deployed API failures including 404/missing-file responses, and explicitly exclude already-captured API failures from agent-browser. Then encode one routing example as a regression case.

Recommended changes

1Broaden the incident trigger

Skill metadata

Cover unexpected test-stage 4xx/5xx responses, missing records/files, and failures reported during manual testing. The description is the primary discovery surface.

2Add a browser negative trigger

Skill metadata

State that a URL, the phrase “manual test,” or a known API response is not enough. Use browser automation only when navigation, interaction, DOM state, network capture, or visual reproduction is actually needed.

3Add a fast-path gate

Skill procedure

When status, response body, and failing endpoint are already supplied, skip browser reproduction and start with the narrow backend evidence path. Browser escalation remains available if the UI is needed to reproduce or correlate the request.

4Keep a trigger regression matrix

Validation

Record representative prompts with expected and excluded skills. This catches semantic overlap that structural skill validation cannot detect.

Proposed routing language

auditflow-live-incident:
Use for AuditFlow test-stage deployed failures, including unexpected 4xx/5xx responses,
missing-record or missing-file errors, and failures reported during manual acceptance testing.
When the endpoint, status, and response are already supplied, start from API/log/data evidence
without browser reproduction. Do not use for production mutation, ordinary local debugging,
broad release validation, or full E2E testing.

agent-browser (negative trigger):
Do not use solely because a report contains a URL, says “manual test,” or concerns a web app.
For an already-captured API response that can be diagnosed from code, logs, configuration, or
data, use the relevant incident/debugging workflow. Use browser automation when interactive or
rendered browser state is evidence needed to reproduce or verify the failure.
